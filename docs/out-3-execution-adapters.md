# OUT-3 execution adapter contract

The scheduler in `server/agent-manager.mjs` owns supervision, persistence, recovery and capacity. Everything provider-specific lives in an adapter under `server/execution-adapters/`, and the registry in `index.mjs` is the only list of providers. Persisted conversations and runs store the adapter id, so ids are permanent.

## Contract version 1

| Field | Meaning |
| --- | --- |
| `kind` | `harness` drives an external agent CLI that authenticates itself. `direct-provider` is Outright-managed execution against a model API. |
| `modelProvider`, `authority` | The model vendor and where authority comes from. A harness uses its own CLI login. A direct provider names its own environment credential; a harness login never grants API access, and there is no fallback between them. |
| `environment` | Direct providers only: the `OUTRIGHT_*` variables the adapter reads. They are removed from every spawn and handed only to that adapter's process. |
| `detect` | Direct providers only: checks the credential and endpoint settings, so an unusable configuration is reported as unavailable before anything is queued. |
| `versions` | The oldest verified version and the first unverified major. Anything outside the range, a prerelease such as `0.162.1-rc.1`, or an unparseable `--version` is reported as incompatible. |
| `capabilities` | Approval policies mapped to native permission modes, suggested models and whether custom names are allowed, reasoning efforts, resume support, structured output (`jsonl`), read-only support, hosted suitability and whether the provider reports usage windows (`usageLimits`). |
| `accounts` | Harness adapters only, optional: the CLI's home variable and standard home, the arguments of its login status command, a parser that keeps only display fields, rules for the credential variables an added account runs without (names or `*` patterns, with explicit non-credential exceptions), the ones the CLI reads but never authenticates with in place of its login (`inertCredentials`), the switches that count only when enabled, and the sources its status command cannot report (`unreportedCredentials`), the only ones that make the default login configured without a check. Its parser says whether a login is the one stored in the home (`ownLogin`). See [OUT-28](out-28-provider-accounts.md). |
| `sessionIdentity` | The native field carrying the provider's session id. Resume uses only a session created by the same adapter. |
| `buildLaunch`, `normalize` | Argv construction and stream normalization. Positional values follow `--`, so a prompt or session id can never become an option or subcommand. |

Normalized events are `session`, `assistant.delta`, `assistant.message`, `tool.started`, `tool.completed`, `usage`, `model`, `rate_limit`, `provider.failure` and `provider.event`. A `rate_limit` event carries the usage windows a provider reports for its login; see [OUT-28](out-28-provider-accounts.md). Usage and failure events keep provider detail under `native`, and unknown records remain `provider.event`. A `provider.failure` marked `terminal: true` (Codex `turn.failed`, a Claude Code `is_error` result, an Anthropic `error` event) fails the run even if the process exits 0. A non-terminal failure, such as a Codex top-level `error` notice that may precede a retry, only explains a nonzero exit.

## Validation order

1. When a run is submitted or recovered, the runtime checks the adapter, approval policy, model name, reasoning effort and resume support against the declared capabilities. A known value the adapter does not support returns `409 PROVIDER_CONFIGURATION_UNSUPPORTED` or `PROVIDER_RESUME_UNSUPPORTED`. A malformed value, such as an unknown approval policy or effort, an unsafe model name or a badly formed session id, returns `400 PROVIDER_CONFIGURATION_INVALID` or `PROVIDER_SESSION_INVALID`, and the raw value is not echoed. Settings, new chats and chat edits apply the same model name rule as launch, so an unsafe model is refused when it is saved (`400 PROVIDER_CONFIGURATION_INVALID`) rather than on every later send. Saved defaults fill only fields the request omits or sets to `null`; a supplied `false`, `0` or `""` provider, approval policy or effort is rejected as malformed, and an explicit empty model selects the adapter default. Nothing falls back silently.
2. Next, a fresh discovery probe checks availability and version compatibility. A missing provider returns `409 PROVIDER_UNAVAILABLE`, and an out-of-range version returns `409 PROVIDER_INCOMPATIBLE`. Both checks finish before any message or run row is written.
3. At launch, the scheduler builds the argv through the same validation. A queued run that has become invalid fails with that message instead of starting.

A run saved before model names were validated may hold a model that is no longer safe to launch. Resume and retry refuse it with `409 RECOVERY_MODEL_UNLAUNCHABLE`. After the user confirms, the same request with `useProviderDefaultModel: true` continues with the provider's default model. The interrupted run keeps its original model, and nothing else about the run changes. A session id saved before the format rule cannot be resumed (`400 PROVIDER_SESSION_INVALID`), but retry still starts a fresh session. The database applies the same session rule to every recovery.

Switching a conversation's provider clears its stored session unless the same edit attaches a new one. Attaching a session to a conversation whose adapter cannot resume returns `409 PROVIDER_RESUME_UNSUPPORTED`. Attach, launch and provider-emitted session ids all use the same format rule. An attached id that breaks it returns `400 PROVIDER_SESSION_INVALID`, and an emitted id that breaks it is not stored, so a stored session can always be resumed.

A conversation's session belongs to a session epoch. Any edit that changes its provider or session, including a recovery retry or resume, starts a new epoch. An ordinary send reads the epoch at launch, together with the session it resumes. A recovery resume or retry keeps the epoch of its recovery decision, because that is when its session was chosen. A run copies its native session back to the conversation only while that epoch is current, both when the provider emits the id and when the run finishes. A switch away and back, an explicit clear or an attach made during a run, or while a recovery run waits to launch, therefore survives the run's late writes, and the next send starts from the conversation's session, not the discarded one. The run row always keeps its own native session. Edits to other fields, such as the title, do not start an epoch, and the conversation settings dialog sends the session field only when the user changes it.

## Credentials and environment

Each run spawn gets a scoped environment. `OUTRIGHT_*` runtime settings are never inherited. A direct provider receives only the `OUTRIGHT_*` variables it declares.

Every server process starts through `server/child-process.mjs`. Its `spawn`, `spawnSync`, `execFile` (including the promisified form) and `execFileSync` apply `withoutDirectProviderCredentials()` to whatever environment the caller passes or inherits. They accept Node's optional-argument forms: `null` or omitted arguments keep the options and callback in place. That function removes the declared variables case-insensitively, as Windows requires. The scoped functions cover harness `--version` probes, git and gh utilities and the repository hooks they run, editors opened from a worktree along with the terminals, tasks and language servers they start, native supervisor control and recovery commands, integrated terminal brokers, and system tools such as `ps`, `sysctl`, `icacls`, `taskkill` and `powershell`. `launchDetached` and the utility runner also filter their own environment explicitly. Only `spawnExecution` passes an environment through unchanged, and only the adapter run launch uses it, with the environment from `buildExecutionEnvironment()`. Inside that run, the launch wrapper's own identity helpers start by absolute path, PowerShell from `%SystemRoot%\System32`, never by a lookup that could resolve to a file in the worktree, and they get the run's environment without the declared variables. `server/child-process.test.mjs` fails if any other server module imports `node:child_process` or `node-pty`, or if the wrapper's helpers lose those properties. Its reviewed exceptions are the PTY broker, whose terminal environment drops all `OUTRIGHT_*` variables, and the wrapper. On macOS a launchd job does not inherit its caller's environment, so the supervisor hands the run's command and environment, including the direct-provider key, to the launched helper through a file in a private temporary directory (directory `0700`, file `0600`, created exclusively and without following links). The helper reads and unlinks the file before starting the provider. If a crash prevents that, the file stays until the recovery probe or `--terminate` for that run's label removes it along with the directory. The runtime process itself still holds the key in its own environment, where same-user tools such as `ps -E` can read it. Protecting the key from other processes of the same user is outside this boundary.

A harness CLI inherits the rest of Outright's environment unchanged, and that is its effective authority. For example, Claude Code honours an `ANTHROPIC_API_KEY` exported for Outright, just as it would in a shell. Enabling the direct provider cannot change that, because its key lives in `OUTRIGHT_ANTHROPIC_API_KEY`. The direct provider also never reads `ANTHROPIC_API_KEY`, so a key set up for a harness cannot become direct-provider authority.

The Anthropic runner sends its key only to the configured endpoint. That endpoint must be https or a loopback http address with no user name or password, and discovery applies the same check, so a bad endpoint is unavailable before anything is queued. Network failures report only an error code, never the endpoint URL. A provider or gateway that reflects the key in an error body or any streamed event, verbatim or inside JSON-encoded text it nests in a message, has every occurrence replaced with `[redacted]` in the parsed values before the record is serialized, so it never reaches run events or the run error. Text deltas are redacted as one stream, because Outright joins them into one answer: text that could begin the key is held until the next delta, and released before the runner exits, so a key split across deltas never reaches the transcript. Requests go to `v1/messages` under the base URL's path, as with the Anthropic SDKs, so a gateway at `https://host/anthropic` receives `/anthropic/v1/messages`. Redirects are refused rather than followed. A streamed event is limited to 1 MiB in total: its data lines, joined by line feeds, are held as bytes, so the limit is the memory the event uses however many lines it arrives in. A malformed event fails the run, but text that has already streamed is kept. So does an event without a type, or a recognized event missing a field Outright reads, such as a content delta without a type or a text delta without string text; delta types Outright does not read are ignored. Each request asks for at most 8192 output tokens. A response that stops at that cap, or at the model's context window (`model_context_window_exceeded`), fails the run with a message saying it was truncated, and keeps the text it streamed and its usage. A final `message_delta` without a non-empty string stop reason also fails the run and keeps its text and usage. The stream must follow the message lifecycle: `message_start`, its content blocks, `message_delta`, then `message_stop` as the last event. Pings, errors and event types Outright does not know may appear anywhere before `message_stop`. Each content block is `content_block_start`, deltas for that block's index only, then `content_block_stop`. One block is open at a time, its index is above every earlier block's, and none may be open at `message_delta`; a block with no deltas is valid. A stream that breaks that order fails the run, for example one with no `message_start`, a second `message_start`, `message_stop` before `message_delta`, a delta outside its block, a reused block index, or anything after `message_stop`. The text streamed before the break is kept, and nothing after it is forwarded. Lines may end in CRLF, LF or CR, including a CRLF split across reads. The runner waits for stdout to drain, so it stops reading from the API while Outright is not consuming its output.

## Adapters

| Adapter | Kind | Supported versions | Notes |
| --- | --- | --- | --- |
| `codex` | harness | 0.162.1 up to, but not including, 1.0.0 | Sandbox modes map one-to-one. Resume uses `exec resume` with a config override for the sandbox. Only `command_execution`, `file_change`, `mcp_tool_call` and `web_search` items become tool events; reasoning, plans and other items stay `provider.event`. Every success line of `codex login status` is recognized; workload identity is read only from the environment, so it signs in the default login and never an added account. |
| `claude` | harness | 2.1.296 up to, but not including, 3.0.0 | Policies map to `plan`, `acceptEdits` and `bypassPermissions`. |
| `anthropic-api` | direct-provider | runner 1.x | Requires `OUTRIGHT_ANTHROPIC_API_KEY`. `OUTRIGHT_ANTHROPIC_BASE_URL` optionally overrides the endpoint. It is read-only because it has no tools, does not resume, uses the model's default effort and accepts only https or loopback endpoints. |

Adding an adapter means adding a module, registering it, adding fixtures under `tests/fixtures/execution-adapters/<id>/` (enforced by `server/execution-adapters.test.mjs`) and recording live evidence. Each harness's minimum is the version its fixtures were recorded from: 2.1.296 for Claude Code and 0.162.1 for Codex. An older CLI is reported incompatible rather than assumed to accept the current argv; lowering a minimum needs fixtures recorded at the new floor. Adapters are trusted code shipped with Outright. Loading user-supplied adapters at runtime is out of scope until there is a trust policy for them.

## Deferred to OUT-38

Model, approval policy and reasoning effort are still global defaults, not per-provider ones. Changing the default provider in Settings changes nothing else. If the new provider cannot honour the saved policy or effort, the value stays selected, marked not supported, and Save stays disabled with an announced reason until the user picks a supported one. After a provider switch, in Settings or in a conversation, the model is kept only if the new adapter lists it; otherwise Save stays disabled until it is replaced or cleared. A shared vendor is not enough: Claude Code's `sonnet`, `opus` and `haiku` aliases are not Messages API model IDs. Each control the announcement blames is marked invalid and described by it. A chat with no model of its own inherits the default model only when it runs the default provider; on any other provider it uses that provider's default. Because these defaults are global, a supported choice made for `anthropic-api` also applies to chats on other providers. A chat switched to `anthropic-api` while the default policy is `workspace-write`, or while the default effort is not `medium`, is therefore rejected with `409 PROVIDER_CONFIGURATION_UNSUPPORTED`. Outright does not substitute a supported value. The error names Settings as the place to change the default. The default-model suggestions also follow the default provider, even though chats on other providers share the same field. Per-provider and per-role execution profiles belong to [OUT-38](https://linear.app/21n/issue/OUT-38/configure-reusable-execution-profiles-per-workflow-task-and-agent-role).
