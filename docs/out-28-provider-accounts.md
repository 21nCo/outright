# OUT-28 provider accounts and usage

`server/provider-accounts.mjs` owns the account inventory, switching and usage presentation. The scheduler in `server/agent-manager.mjs` asks it which account a launch uses and records the answer on the run.

## Accounts

| Provider | Default account | Added accounts | Identity check |
| --- | --- | --- | --- |
| `claude` | The login of whatever `CLAUDE_CONFIG_DIR` Outright's environment selects (the exact name; any spelling on Windows), or `~/.claude` when it is unset | A `CLAUDE_CONFIG_DIR` directory | `claude auth status --json` |
| `codex` | The login of whatever `CODEX_HOME` Outright's environment selects, or `~/.codex` when it is unset | A `CODEX_HOME` directory | `codex login status` |
| `anthropic-api` | `OUTRIGHT_ANTHROPIC_API_KEY` | None; it is a direct-provider credential, kept separate from harness logins (OUT-3) | The adapter's `detect()` |

An added account is a name and a directory the user owns. The user signs in from a terminal with the CLI itself, for example `CLAUDE_CONFIG_DIR=/path claude auth login`. Outright stores only the resolved directory path and never reads, copies or logs anything inside it. A path that is relative, missing, not a directory, owned by another user (on Windows, outside the user's profile, since Node reports no owner there), already added, or the default login's directory under any path (the variable's directory, or the standard one when it is unset, through links) is refused with `400 PROVIDER_ACCOUNT_INVALID` or `409 PROVIDER_ACCOUNT_DUPLICATE`. Each provider can have 16 added accounts.

A relative `CLAUDE_CONFIG_DIR` or `CODEX_HOME` would be resolved by the CLI in each run's worktree, so it names no one directory to check or key. Neither does an absolute one whose `..` follows a link or a part that does not exist: `/a/link/..` is `/a` when the `..` is removed by name, as Node's `path.join` does, but the link target's parent when followed on disk, so CLIs may use different directories. A `..` that crosses no link names one directory and is keyed by it. While the variable is relative or has such a `..`, the default login is `unknown`, naming the variable and never its value, without running the status command; sends with it and switching to it are refused (`409 PROVIDER_ACCOUNT_UNAVAILABLE`, `409 PROVIDER_ACCOUNT_SWITCH_FAILED`) until the variable is a full path without such a `..`. Added accounts are unaffected.

A CLI home has one key, used for every record, comparison and partition: the directory it leads to through links, as the operating system names it (the native `realpath`, so a case-insensitive volume gives the stored case and Windows expands 8.3 and `subst` names; a part that does not exist yet keeps its name under its nearest existing directory), case-folded on Windows. Adding an account resolves its directory the same way, so `/Users/me/WORK` and `/Users/me/work` on a case-insensitive volume are one directory. With the variable unset, it is the directory the CLI's standard home (`~/.claude`, `~/.codex`) leads to at launch, so an unset variable and one naming the standard home are one key, and repointing a linked standard home to another directory is another login. Runs, recovery pins, measured usage, limit windows and duplicate checks all use it, so `/d`, `/d/.`, `/d/` and a link to `/d` are one login with one history. A key is a directory path: swapping a directory's contents in place (for example with `mv`) keeps its key, and Outright cannot detect it. A session or recovery continues only under the key it launched with, for every account: if an added account's directory is replaced by a link to another directory, its existing sessions and recovery pins are refused (`409 PROVIDER_ACCOUNT_UNAVAILABLE`, naming both directories) until the directory is restored, and its usage and limits from then on are kept apart from the earlier directory's. An added account whose directory the environment later selects for the default login is the same login under two ids: Settings flags it, switching to it fails with `409 PROVIDER_ACCOUNT_DUPLICATE`, and a new session with it active is refused the same way. Chats that already have a session on it keep it.

A run's login is its home key plus where its credential came from. When credential sources (below) stand in for the default login, the login key is the name of every one set, sorted and joined by `+`, and the home key (`ANTHROPIC_API_KEY:/Users/me/.claude`, `ANTHROPIC_API_KEY+CLAUDE_CODE_USE_BEDROCK:/Users/me/.claude`), so adding or removing any of them changes it whichever the CLI gives precedence; a login from the home itself is the bare home key, as runs recorded before this were. Runs, recovery pins, cached login checks, measured usage and limit windows all use the login key. Restarting Outright with such a variable newly set, or unset, refuses the sessions and recoveries launched under the other source (`409 PROVIDER_ACCOUNT_UNAVAILABLE`, naming both sources and never a value) and keeps their usage and limits apart until the environment is restored. Giving the same variable another value keeps its key, which Outright cannot detect, like swapping a directory's contents in place.

Identity checks run the CLI's own status command through the same supervised probe as version checks, with the account's home variable set and every direct-provider credential removed. Credential sources are declared by rule, not as a list of names, so a source the CLI adds under a known prefix is covered: for Claude Code every `ANTHROPIC_*` variable (keys, tokens, profiles, federation and organization selectors, identity tokens, base URLs), every `CLAUDE_CODE_USE_*` provider switch, and the `CLAUDE_CODE_OAUTH_*`, `CLAUDE_CODE_API_KEY_*`, `CLAUDE_CODE_GATEWAY_*`, `CLAUDE_CODE_HOST_*`, `CLAUDE_CODE_FEDERATION_*`, `CLAUDE_CODE_SDK_HAS_*`, `CLAUDE_CODE_CLIENT_KEY*`, `CLAUDE_CODE_ACCOUNT_*` and `CLAUDE_CODE_ORGANIZATION_*` families, `CLAUDE_CODE_SESSION_ACCESS_TOKEN`, `CLAUDE_CODE_WEBSOCKET_AUTH_*` and `CLAUDE_CODE_CUSTOM_OAUTH_URL`; for Codex every `OPENAI_*` variable and every `CODEX_*` variable naming a key, token, auth, federation or identity (`CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`). An explicit list of exceptions, checked against Claude Code 2.1.303, chooses models, betas, logging or a tool rather than a login: `ANTHROPIC_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, `ANTHROPIC_DEFAULT_*`, `ANTHROPIC_CUSTOM_MODEL_OPTION*`, `ANTHROPIC_BETAS`, `ANTHROPIC_LOG`, `CLAUDE_CODE_USE_NATIVE_FILE_SEARCH`, `CLAUDE_CODE_USE_POWERSHELL_TOOL`, `CLAUDE_CODE_USE_COWORK_PLUGINS` and `CLAUDE_CODE_USE_CCR_V2`. An added account's check and launch drop every source, case-insensitively on Windows. The default account keeps them, as part of whatever the environment selects, and every source set stands in for the default login, except `OPENAI_API_KEY` for Codex: Codex 0.162 does not authenticate with it (a signed-out home with only `OPENAI_API_KEY` set fails with a missing-authentication error), so it never hides the home's login. When one is set (a `CLAUDE_CODE_USE_*` switch only when Claude Code reads it as enabled: `1`, `true`, `yes` or `on`), it keys the default login (see below), but a source is not proof of a login: an endpoint, profile or selector alone signs nothing in. The default login's check therefore runs the status command with its sources set, and its result names the variables, never their values. Claude Code 2.1.304 reports every source that signs it in (`ANTHROPIC_API_KEY` as `api_key`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` as `oauth_token`, an enabled provider switch as `third_party`) and a signed-out home with only `ANTHROPIC_BASE_URL`, `ANTHROPIC_PROFILE`, federation selectors or `CLAUDE_CODE_USE_GATEWAY` as signed out. `codex login status` (0.162.1) reports `CODEX_ACCESS_TOKEN` (`access token` or `personal access token`) and workload identity (`workload identity`, whenever `OPENAI_FEDERATION_RULE_ID` or `OPENAI_IDENTITY_TOKEN_FILE` is set) but ignores `CODEX_API_KEY`, so for Codex only `CODEX_API_KEY` makes the default `configured` without running it; with any other source the home is checked. A default login signed in either way neither blocks a send nor a switch back to it; a signed-out one fails the switch (`409 PROVIDER_ACCOUNT_SWITCH_FAILED`, the active account unchanged) and refuses a send. An added account is signed in only by a login stored in its directory, whatever source the rules miss: Claude Code reports how it signed in, and only a claude.ai login or a Console key from `/login` (`apiKeySource` `/login managed key`) counts. Any other method (Claude Code 2.1.303 prints `oauth_token` for an empty directory with only dummy federation selectors inherited, `api_key` with an environment `apiKeySource`, `api_key_helper` or `third_party`) lists the account as signed out, keeps none of that login's details, fails a switch (`409 PROVIDER_ACCOUNT_SWITCH_FAILED`) and refuses a send before anything is written (`409 PROVIDER_ACCOUNT_SIGNED_OUT`). `codex login status` does not say where a key or token came from, so a Codex account relies on its check running without every source: a ChatGPT, API-key, access-token, personal-access-token or Amazon Bedrock login it then reports can only be stored in the account's directory. Workload identity is read only from the environment, so an added account that reports it is signed out. Added accounts are always checked by their home's login. Both CLIs exit 1 for a signed-out login, which the check accepts. Only display fields are kept: signed in or out, method, email, organization and plan. Codex prints a masked key after an API-key login; only the method is kept. A check that fails or prints something unrecognized is `unknown`, and its message never quotes CLI output. Checks run one at a time, each bounded to 5 seconds. A check someone waits for (a switch, **Check**, an add or a send's recheck) runs before every background recheck that has not started; a queued background check of the same account is moved ahead rather than repeated. Results are cached in memory with the time they were made, which Settings shows next to each login, and the login key they were made under. A result made under another key, because the account's directory now leads elsewhere, is never shown, recorded with a run or trusted: Settings shows the login as checking and checks it, a launch records no identity, and a send waits for a new check and is refused if it finds the login signed out. A check is evidence only for the login key that was current both when it started and when it ended: one during which the directory or credential source changed is kept for neither key, and a switch or send never shares a check started under another key. It waits for a check of the current key, once more if that one also spanned a change, and the switch fails (`409 PROVIDER_ACCOUNT_SWITCH_FAILED`, the active account unchanged) or the send is refused before anything is written when that login is signed out or still could not be checked under one key. A result older than 10 minutes is checked again in the background when the account is listed or a launch resolves it, so a re-login in a home is seen without **Check**. The identity a run records is the latest check's when it launched: a launch that finds it older than 10 minutes still records it, and checks again for later launches. A failed check, including a storage fault after its probe, fails only its own callers. An add whose check fails still succeeds once the account is written; its login is listed unchecked and is checked again when listed. A probe whose process tree could not be proven stopped ends identity checks for that CLI until restart, and shutdown reports it, as provider discovery does. Listing accounts checks an account that was never checked or was checked over 10 minutes ago; **Check** in Settings and every switch check again.

## Switching

`PUT /api/provider-accounts/active { provider, accountId }` checks the account's login first. A signed-out, unknown or removed account fails with `409 PROVIDER_ACCOUNT_SWITCH_FAILED`, and the active account does not change. Switches for one provider apply in request order. A successful switch writes a `provider-account.switched` audit entry naming account ids only.

The active account is a launch-time default:

* A run resolves its account once, when it leaves the queue, and records the account id, its name, the identity known then and the CLI home it launched with (`run_accounts`, by the home key above). A deferred admission is still queued and resolves again; once a run is launching, its account cannot change (`409 RUN_ACCOUNT_IMMUTABLE`). The record is written in the transaction that writes the `launching` marker and confirms an added account still exists, so a run with an account record has always launched, a run whose marker is refused has none (no measured usage, no recovery pin), and an account removed while the launch was prepared fails the run before anything spawns. Just before that, with no wait in between, the account's directory is resolved again: if it now leads to another home than the one resolved for the launch, the run fails (`409 PROVIDER_ACCOUNT_UNAVAILABLE`, naming both) and nothing spawns.
* A launch that resumes a session uses the account of the run that last launched in that session. Switching never moves an existing session, and a chat keeps its session's account until the session is cleared. A session created only by runs from before accounts existed used the default login and resumes with it. A run that never launched, such as a queued run or a recovery that carries the session, does not own it. Ownership is looked up per chat: a session no run in this chat launched in (attached by hand, including one copied from another chat) uses the active account.
* Every account's recorded home matters. The default account follows the environment: a session it created under one home is refused (`409 PROVIDER_ACCOUNT_UNAVAILABLE`, naming both homes) when the environment now selects another, rather than resumed under the wrong login. An added account's session is refused the same way when its directory now leads elsewhere.
* A recovery resume or retry uses the account the interrupted run launched with. The recovery run stores that pin (`run_account_pins`) in the transaction that creates it, so a restart before it launches, and any later recovery of it, keep the account. A run that launched before accounts existed used the default login in a home nobody recorded; its recovery is pinned to the default login with the home marked unknown (`home_known = 0`), like a session from before accounts. A run that never launched has no account to keep and uses the active one. A recovery whose account was removed is refused and can only be discarded: adding the same directory again creates a new account, which the pin does not follow. A recovery whose default-login home changed is refused until the home variable is restored or the run is discarded. A resume of a session the interrupted run did not record (one attached to the chat by hand) is refused (`409 PROVIDER_ACCOUNT_UNAVAILABLE`, naming both accounts or sources) when another account or login key last launched in that session, before the recovery decision is recorded, so retry and discard stay available.
* A run that is already running keeps the environment it was spawned with.
* The launch environment sets the account's home variable under its exact name, replacing any other spelling, and drops the credential variables above. The default account changes nothing.

Nothing falls back to another account. A send whose account was removed fails with `409 PROVIDER_ACCOUNT_UNAVAILABLE` before its message or run is written, and a queued run whose account was removed fails at launch with the same explanation. If the last check found the account signed out, a send checks again and fails with `409 PROVIDER_ACCOUNT_SIGNED_OUT` if it still is. A queued run is checked the same way when it leaves the queue, with the account a recovery or resumed session is pinned to, never the active one instead. It fails with that error before its launching marker, account record or spawn if its login is still signed out, or if a check finds it signed out while the launch is prepared. The run launches only with the account and login key that check was made for; if another one resolves by then, it fails with `409 PROVIDER_ACCOUNT_UNAVAILABLE`. Otherwise the CLI reports its own authentication failure. The active account cannot be removed (`409 PROVIDER_ACCOUNT_ACTIVE`), and the default login cannot be removed at all. Removing an account leaves its directory and login untouched, and the runs it launched keep the recorded name.

## Usage

Settings shows two kinds of usage for every account, never mixed:

* **Measured by Outright**: runs launched with the account and its home in the last 5 hours and 7 days, with their tokens and the cost providers reported. Runs without reported tokens or cost, and runs that reported only input or only output tokens, are counted separately: a partial sum is shown as "at least" with the known tokens, and only a window where no run reported either counter is "not reported", never zero.
* **Reported by the provider**: usage windows from Claude Code's `rate_limit_event`, normalized as the `rate_limit` event with each window's utilization, status and reset time. The latest report of each window wins, whichever run sent it, and it records that run. Windows are kept per account, home key and window name, at most 8 per account home, so a report under one default-login home never replaces another's, and returning to an earlier home shows its windows again. A removed account records none. A window whose reset time has passed is shown as reset, without its old utilization. A report older than 30 minutes is shown as stale with its time. A malformed value is dropped rather than guessed. Codex and the Anthropic API do not report usage windows to Outright, so their limits are shown as unavailable, not zero.

Both kinds change with time alone, with no run or account event to announce it. Each measured window carries `changesAt`, when its oldest counted run leaves it. While Settings is open it lists again at the earliest `changesAt`, reset or stale time, and when the tab is shown again; the wait is measured on the runtime's clock (`generatedAt`) and is at least one second, so a skewed client clock neither ages values early nor reloads in a loop. If that reload fails, limits still age in place, and a measured window past its `changesAt` keeps its totals only as a dated snapshot marked out of date, retried every 15 seconds and when the tab is shown again until a reload succeeds.

Each conversation shows the account of its latest run in the header, on its own line that stays visible, shortened with an ellipsis, at 920px and below where the rest of the run summary is hidden. So a queued or running run is named at every width before its first answer, while earlier history is read and after a run that gave no answer. A run queued before it had an account is named as soon as its launch reports one (`run.started`), not when it ends. Each answer stores the account of the run that produced it, so earlier pages and find results name it too. An earlier run that gave no answer (failed, stopped or never launched) is named only by `GET /api/runs/:id`.

## Storage

`provider_accounts`, `provider_account_selection`, `provider_limit_windows`, `run_accounts`, `run_account_pins` and `deleted_run_usage` are new tables, so the migration is additive and needs no backfill. Their `home_path` columns other than `provider_accounts.home_path` hold the login key. The first five count toward the retained-history budget. Adding an account and recording a usage window are optional writes that obey the budget; switching and recording a launch's account are critical writes. `run_accounts` and `run_account_pins` are deleted with their run. A deleted run launched in the last 7 days leaves its account, login key, launch time, tokens and cost in `deleted_run_usage`, so deleting an archived chat does not shrink measured usage; those rows hold no content, are pruned once older than 7 days and are not charged to the budget, so deleting history is never refused for space.

## API

| Route | Result |
| --- | --- |
| `GET /api/provider-accounts` | Every provider with its accounts, active account, login, measured usage and limits |
| `POST /api/provider-accounts` | Add `{ provider, label, homePath }`; `201` with the new listing |
| `PUT /api/provider-accounts/active` | Switch `{ provider, accountId }` |
| `POST /api/provider-accounts/:id/refresh` | Check the account's login again |
| `DELETE /api/provider-accounts/:id` | Remove an added account |

Changes are announced as `provider-accounts.changed`, at most once every 250 ms. A run's launch is one, since its account's measured usage counts it from then, so open Settings shows a running run without waiting for it to end. The client counts them separately (`accountsVersion`) instead of passing them through the shared runtime event that carries terminal output, so they never displace an output chunk. Every listing carries `revision: { runtime, sequence }`: `runtime` names the runtime instance and `sequence` grows with each listing it computes. Settings never shows a listing older than the one it shows, whichever response arrives last, so a delayed action response cannot replace the listing another client's switch produced, and an action does not discard a load that started after it. An action's announcement and focus follow the listing that is shown: a switch overtaken by another change says which account is now active, and focus moves to the switched account's **Check** only if it is still on that account's **Use** button.
